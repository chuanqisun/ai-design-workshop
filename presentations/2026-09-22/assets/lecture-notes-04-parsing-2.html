Top-Down Parsing

Recursive descent, leftmost derivations, and how we massage a grammar until a parser can decide which production to apply without guessing.

1. Where we are: characters → words → sentences

The lexer already ran. Parsing starts from a token stream, not raw text.

source:  2 - 2 * 2
lexer:   Int(2)  -  Int(2)  *  Int(2)
parser:  ??? → parse tree

Tokens: { + , - , * , / , Int } where Int = [0-9]+. Terminals = tokens. Non-terminals = the names on the left-hand side of productions.

Today's grammar

1)  Start -> Expr
2)  Expr  -> Expr + Term
3)  Expr  -> Expr - Term
4)  Expr  -> Term
5)  Term  -> Term * Int
6)  Term  -> Term / Int
7)  Term  -> Int

The two-level split (Expr over Term) is not decoration — it is how precedence gets baked into the grammar. * and / live deeper in the tree, so they bind tighter.

2. Two directions: recognition vs. generation

Recognition (bottom-up)

Start at the string. Match a right-hand side, replace it with the left-hand side. Repeat until you reach Start. Productions applied in reverse. 

Int - Int * Int
Term - Int * Int
Expr - Int * Int
      ...
Expr
Start   ✓ in the language
Generation (top-down)

Start at the start symbol. Match a left-hand side, rewrite it to its right-hand side. Repeat until only terminals remain — then compare to the input. 

Start
Expr
Expr - Term
Term - Term
      ...
Int - Int * Int  ✓ matches

Either way, the sequence of productions used is the derivation, and the derivation is the parse tree. Today we implement the generative direction: top-down / recursive descent.

Check yourself: why is Expr -> Term a bad first choice for input 2 - 2 * 2?

Because from Term you can only ever generate Int (* | /) Int ... — no - can ever appear. You'd consume the whole derivation with input left over and get stuck. The choice of production is a policy decision, and bad policies dead-end.

3. Leftmost derivation, step by step

The rule the parser follows on every single step:

look at the LEFTMOST symbol of the sentential form
  non-terminal → choose a production and apply it (rewrite)
  terminal     → match it against the next input token (eat it)
done when sentential form is empty AND input is empty

A sentential form is just any sequence of terminals and non-terminals produced along the way. The parser keeps three pieces of state, and each has a different personality:

State Behaviour
Parse tree Additive — only ever grows, top-down
Sentential form Mutable — rewritten in place at each expansion
Remaining input Subtractive — a pointer marching left to right
Input
Sentential form
Action taken
Parse tree

Notice what changes at each step. An expand touches the tree and the sentential form but never the input pointer. A match touches the sentential form and the input pointer but adds nothing new to the tree. That asymmetry is the whole algorithm.

4. The policy problem — and the left-recursion trap

How does the parser know to pick rule 3 rather than rule 2 or 4? Naive answer: backtracking search. Try one, and if it fails, back up and try another.

Any search needs three components — a space, an algorithm, and a goal — and two desiderata: it must find the goal and it must terminate. Top-down parsing of this grammar fails the second one. Watch:

Sentential form (expanding leftmost Term via Term -> Term * Int)
Input consumed
0 tokens — nothing ever gets eaten

Diagnosis: the production Term -> Term * Int is left recursive — the leftmost symbol of the right-hand side is the same non-terminal we started with. A recursive-descent parser calls parseTerm(), which immediately calls parseTerm(), having consumed zero tokens. Infinite recursion. Stack overflow. Not a policy problem we can search our way out of — we must rewrite the grammar.

5. Eliminating left recursion

The general transformation pattern:

Left recursive
A -> A α
A -> β

(α, β do not start with A)

Right recursive equivalent
A  -> β R
R  -> α R
R  -> ε

Same language. Now every path begins by consuming β.

Intuition: the original generates β α α α …. The new one produces exactly that, but builds it left-to-right instead of by peeling recursion off the left edge.

8. From grammar to code

    
The payoff: once the grammar is non-left-recursive and LL(1), the parser almost writes itself.

    

      

        Grammar element
        Code element
      

      

        Each non-terminal
        One function, returning a parse-tree node
      

      

        Each alternative production
        An if branch keyed on the look-ahead token
      

      

        A terminal on the RHS
        match(tok) — consume and advance the input pointer
      

      

        A non-terminal on the RHS
        A recursive call to that non-terminal's function
      

      

        Tail-recursive X' rule
        A while loop (builds left-associative trees)
      

      

        ε production
        The fall-through / loop exit
      

    


    
Token  cur;                      // parser state: current look-ahead
Token  nextToken();              // helper: pull the next token from the stream

Node parseExpr() {               // Expr -> Term Expr'
    Node left = parseTerm();
    while (cur == '+' || cur == '-') {      // Expr' -> (+|-) Term Expr'
        Token op = cur; cur = nextToken();
        Node right = parseTerm();
        left = new Node(op, left, right);   // left-assoc: fold as we go
    }
    return left;                            // Expr' -> ε
}

Node parseTerm() {               // Term -> Int Term'
    if (cur != INT) error("expected integer");
    Node left = new Node(cur); cur = nextToken();
    while (cur == '*' || cur == '/') {      // Term' -> (*|/) Int Term'
        Token op = cur; cur = nextToken();
        if (cur != INT) error("expected integer");
        Node right = new Node(cur); cur = nextToken();
        left = new Node(op, left, right);
    }
    return left;                            // Term' -> ε
}


    

      Recap of the arc: generative top-down parsing needs a policy for choosing productions → naive backtracking search doesn't terminate on
      left recursion → rewrite the grammar to kill left recursion (carefully, preserving associativity) → add one token of look-ahead to make the choice
      deterministic → the resulting grammar maps mechanically onto a hand-written recursive descent parser.
